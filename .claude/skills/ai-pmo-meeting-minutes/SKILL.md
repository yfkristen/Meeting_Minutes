# AI PMO 會議紀錄撰寫

把一場 60 至 90 分鐘的口語討論，壓縮成一頁行政文書體紀錄。壓縮比通常在 20:1 到 40:1 之間，選材因此是這份工作的主體，改寫只是次要工序。逐字稿裡絕大多數內容不會進入紀錄。

紀錄的定位是**對齊用文件**：讀者是同層級的 PMO 成員與其主管，用途是確認交辦事項沒有漏接、確認各案狀態一致。它不是會議實錄，不需要還原討論過程。

## 動筆前必須確認的四件事

逐字稿本身無法提供以下資訊。有些可推，有些必問。

**可沿用或推算，不必問**

- **會議名稱**：本例會名稱固定為「金控AI推動委員會PMO待辦事項討論例會」
- **與會人員名單**：沿用前次名單。這是固定成員的例會，不必重新索取整份名單
- **會議日期**：雙週週四。從逐字稿中的相對時間線索（例如「下禮拜一是 8/10」）回推即可

**必須向使用者取得**

- **結束時間**：起訖時間長短不固定，逐字稿裡也沒有，只能問
- **本次出席狀態**：誰請假、是否有為單一議題列席的新增人員。名單沿用不等於狀態沿用。**把前次的請假註記一併沿用是實際發生過的錯誤**
- **Loop 看板現況**：最好請使用者提供截圖。看板一次解決案名、負責人、進度三件事，比從逐字稿推論可靠得多
- **負責人對應表**（無看板時）：把案名列出來請使用者對應，不要自行猜測後標「待確認」交出去

逐字稿是否有說話者標記只影響改寫的難度，不影響上述資訊的取得方式。

## 輸出格式

固定使用下列結構。編號層級為 壹貳參 → 一二三 → 1. 2. 3.:

```
〔會議正式名稱〕

壹、會議時間：2026/8/6(四)PM4:00-5:40
貳、與會人員：〔姓名〕、〔姓名〕(請假)、〔姓名〕
參、討論議題與會議紀要
一、〔本次主議題〕：
1. 〔交辦內容〕(〔負責人〕)
2. 〔交辦內容〕(〔負責人〕/〔負責人〕)
二、各案進度
1. 〔案名〕：〔狀態〕(〔負責人〕)
2. 〔案名〕：〔狀態〕(〔負責人〕)
三、新增議題：
1. 〔議題〕：〔內容〕。〔後續〕
2. 〔議題〕：〔內容〕。〔後續〕
```

三節的分工：

- **一、本次主議題**：本次為此另外邀請單位列席的那一項。**不下小標**，直接用編號段落，每項結尾標負責人。無主議題時整節省略
- **二、各案進度**：Loop 看板上的既有案件，案名與負責人一律照看板，不自創
- **三、新增議題**：本次新冒出、尚未進看板的事項。**不標負責人**，因為尚未指派

制度性議題（會議目的、會議安排、運作機制）只在新設會議或定位變動時出現，放在最前，其決議寫在該項內。

**壹與貳固定為會議時間與與會人員，不放實質內容。** 會議目的、會議安排都是「參」底下的子項，不佔壹貳層級。這是初稿最常見的結構錯誤：把會議宗旨放在壹、會議安排放在貳，結果基本資料無處可放。

**紀錄本體不含郵件語。**「各位主管好」「檢送……會議紀錄」「敬請參閱」屬於發信正文，不進紀錄。紀錄第一行是會議正式名稱。使用者需要發信時另外提供郵件正文，與紀錄分開。

格式細節：

- 「壹、會議時間」欄用 12 小時制加 AM／PM；正文內提到的時段用 24 小時制（例如「雙週週四16:00-17:00」）
- 請假者列在與會人員名單中，後接半形括號寫「(請假)」，**不附原因**
- 標點一律全形：逗號「，」分號「；」冒號「：」。括號統一半形
- 「一、」「三、」的節標題後帶全形冒號；「二、各案進度」不帶
- 各案進度每項結尾以半形括號標註負責人姓名
- 不寫主席、紀錄人、會議地點、下次會議時間等欄位。會議頻率與時段屬於「會議安排」議題，寫在正文裡
- 沒有獨立的「決議事項」節。決議寫在所屬議題內

## 議題的排序與合併

**依制度層級排，不依發言順序。** 逐字稿的話題會反覆跳躍，同一件事可能散落在開頭、中段與結尾三處，必須全部歸攏到同一項。

順序原則：

1. 本會議的目的與定位（若為新設會議或定位有變動）
2. 會議安排（頻率、時段、出席方式）
3. 運作機制（平台、看板、檔案存放、群組使用方式）
4. 各案進度報告
5. 討論事項

議題標題要能獨立成立，讀者不看內容也知道這項在講什麼。標題可含機制名稱，例如「建立工作同步機制：Teams + Loop 看板」優於「工作平台」。

每一項只放一類資訊。不要在同一項裡混雜情境描述、事實與結論。

## 每一項要寫到什麼程度

案件的分節由看板決定，不由討論性質決定。但一項要寫多長、要不要寫出未決，取決於這次討論產生了什麼。

**判準是這一段有沒有產生新資訊，不是有沒有人開口。**

有問有答也可能沒有新資訊。提問若只是確認既定參數、答案未改變任何安排，該案就只寫狀態。例如「150 分鐘是含 demo 嗎」「可以提早下課嗎」，問完之後課程規劃沒有任何改變，一句帶過即可。

出現下列任一情形，該項需寫到結論或後續，不可只寫狀態：

- **變更**：原訂做法改為另一種。例如取消當天抽籤、改為事前分組
- **認知落差**：兩人以上對現況、歸屬或權責的說法不一致，經說明後才對齊。落差本身不寫，寫對齊後的結論
- **權責重新界定**：某事該由誰承辦、該以什麼角度處理有重新定義。例如功能面比較改由金控數科處負責
- **未決**：結論待定。寫出卡在哪一關與下一步，例如「俟三長確認後定案」「俟需求明確後提三長會議請示」

長度：無新資訊者一句；有變更或未決者一至三句。寫不下就是選材沒收乾淨。

**未決不等於待確認。** 未決是案件本身還沒定，要寫進紀錄；待確認是撰稿者不知道答案，交付前問清楚，不寫進紀錄。

## 修訂會往哪個方向改

以下模式來自第一版與定稿的實際差異。撰寫時先避開，不要等修。

底層原因：紀錄以郵件寄給「各位主管」，包含造成交辦管道分歧的那些人。任何讀起來像在檢討收件人的句子都會被改掉。

**一、目的敘述一律正面表述，不寫問題診斷**

即使是中性的事實陳述，只要指出組織運作有缺陷，就會被改。

| 第一版 | 定稿 |
| --- | --- |
| 交辦管道眾多 | 專案推動涉及多元溝通與交辦管道 |
| 導致資訊碎片化且重複作業 | 為提升資訊整合效率並強化跨單位協作 |
| 避免漏接交辦事項 | 定期彙整重要事項、同步執行進度 |
| 對齊各會議傳出的分歧訊息 | 確保各項決議與訊息傳達一致 |

眾多改多元、漏接改彙整、分歧改一致。方向是把問題改寫成待達成的目標，不留診斷。

**二、管控語彙改協作語彙**

收件人與撰稿人同層級或更高，不用監督語氣。

- 建立工作**追蹤**機制 → 建立工作**同步**機制
- 用於**追蹤**各事項交辦進度 → **列示**各項交辦事項及進度

**三、不寫削弱出席義務或作業義務的表述**

會中確有此共識也不寫。第一版的「並採開放參加性質」在定稿中刪除，彈性改由「原則上」承載，不明文寫成可不參加。

**四、補全受詞、機構全名、時間限定**

| 第一版 | 定稿 |
| --- | --- |
| 功能比較由張老師負責 | Slack與Teams功能比較由張老師負責 |
| 規劃先在推動委員會 | 規劃先在AI推動委員會 |
| 最後抽籤 | 最後抽籤9月工作坊題目 |
| 課程規劃 | 8月課程規劃 |
| 檔案存放於「AI策略藍圖推動」 | 相關檔案已存放於「AI策略藍圖推動」共用資料夾中 |

**五、移除工具操作細節**

介面路徑、點擊位置、地點取得方式都不寫。定稿刪除了「並可在群組『已共用』中直接開啟」與「地點以會通為主」。

**六、口語動詞改書面動詞，並加緩衝詞**

| 第一版 | 定稿 |
| --- | --- |
| 先把檔案丟入此群組 | 可先將檔案於群組中分享 |
| 已完成者直接標「完成」 | 已完成者請標示「已完成」 |
| (四) 16:00-17:00 雙週會形式 | 原則上以雙週週四16:00-17:00 安排會議(雙週會) |
| 若有需求可自行新增 | 請各位自行新增 |

「若有需求可」是給許可，「請各位」是提出要求。需要成員持續維護的機制用後者。

**七、補述作業的目的**

第一版只寫做法，定稿補上理由。「交件前先把檔案丟入此群組，方便互相查看與交流進度」補為「……，以利主管詢問時可先行回答」。

**八、稱謂對象要準**

「各單位」改「各位PMO」。收件人是具名的 PMO 成員，不是單位。

**九、工具能力不可寫成未經確認的功能**

第一版寫「若有需求可自行新增欄位」，但逐字稿的結論是 Loop 欄位型別固定、能否新增待研究。定稿改為「請各位自行新增交辦事項」。凡逐字稿中結論為「不確定可否」者，不得寫成可用。

**十、語音轉檔錯字會殘存到第一版**

第一版照抄了「治安專場」，定稿改為「資安專場」。交付前務必逐項比對校正表。

## 主議題節寫成交辦，不寫成敘述

**前提：當場有人承接、事情已經定案，才寫成交辦。** 沒到這一步就寫陳述，用「將」「已」「待」。

紀錄沒有立場指派工作，它只登記已經成立的交辦。凡是會中還在來回、只有初步方向、或根本沒有人接下的事，寫成「請⋯⋯」就是用紀錄去派工，會被退。實際發生過的錯誤是整節通篇用「請」，其中多數事項當天並未落到任何人身上。

判斷方式：該項若標得出負責人，且該人在會中確實接下，用交辦式；標不出來或對方只回應「我知道了」，用陳述式。

| 敘述式（錯） | 交辦式（對） |
| --- | --- |
| 資訊單位於課前完成主管設備安裝及工具包下載 | 行前訓練的簡報、模擬題目請人資上傳雲端供主管們下載 |
| 8/17董事長出席該梯，另指派助教專責協助 | 8/17金控董事長將出席行前訓練課程，請增派專責助教協助相關事宜 |
| 活動結束後停用並換回原key | 請於工作坊結束時特別提醒或協助主管換回原API Key |
| 證券參訓設備係租賃取得，歸還前應檢查並清除SPADE | 採租賃的電腦設備，請於歸還廠商前務必清除SPADE及相關檔案 |

**交辦事項不寫理由。** 待辦本身就是內容，背景說明一律刪除。例如專用 API key 那項，只留期間（8/10-9/11）與待辦動作，不寫「以避免現用key外流並利於用量監控」。

這與「結論的理由要保留」不衝突：理由若支撐一個結論（例如 Slack 建議不採用的三項事實），保留；理由若只是交辦的背景，刪除。

## 敏感詞一律去識別

紀錄會流通到 PMO 以外，涉及地區、子公司、特定人的表述須改為概括說法。

| 逐字稿／初稿 | 紀錄 |
| --- | --- |
| 中國模型 | 境外模型 |
| 南京子行 | 海外子行 |
| 證券參訓設備 | 採租賃的電腦設備（不點名子公司） |
| 寬董 | 金控董事長 |

## 案件的取捨與命名

- **無實質內容者整項刪除**，不要為了對齊看板而留空殼。只寫得出「刻正研議中」「處理中」的案件不列
- **案名照 Loop 看板，但可精簡**。去掉贅字即可，不要另創名稱。例如「金控資料分級管理框架」→「資料分級管理框架」、「SPADE生命週期(Product Journey)之AI資安管控作為」→「SPADE生命週期之AI資安管控作為」、「強化郵件外寄之管控機制與程序」→「強化外寄郵件管控機制」
- **負責人依案件歸屬，不依當日出席**。負責人請假，其案件仍標其姓名
- **待確認事項在交付前問清楚，不寫進紀錄正文**。使用者手上通常有答案。把「(待確認)」留在紀錄裡等對方填，是把工作退回去

## 會議紀錄與任務追蹤表的分工

同一場會議會產出兩份文件，內容不重述。

| | 會議紀錄 | 任務追蹤表 |
| --- | --- | --- |
| 讀者 | 各位主管，逐次寄送 | PMO 內部，跨會議累積 |
| 範圍 | 本次產生的內容 | 全部案件，含本次未動者 |
| 寫什麼 | 為什麼這樣定、有哪些前提與理由 | 走到哪一關、下一步、時限 |
| 未討論的案 | 整項不出現 | 標「本次未討論／維持前次」 |
| 密度 | 一至三句，可含理由 | 一至兩句，只留狀態與節點 |

追蹤表以任務為列、以會議為欄，一列一任務、各次會議進度並排。案名與編號沿用 Loop 看板，本次新增的議題接在既有編號之後。

**追蹤表最容易做錯的是把紀錄整段搬過去。** 例如資料分級一案，紀錄寫「法遵長指示須與子公司對齊，避免各定一套標準致對接成本過高」，追蹤表只需「框架定調金控訂原則、子公司留彈性」。理由留在紀錄，追蹤表留節點。

**里程碑要留，中間關卡要收。** 逐一列出每一道核決是流水帳；只留兩個日期節點又看不出風險。寫法是留下有日期的節點，加一句點出排程限制的實質原因。例如「8/28確認版本後尚須經數道核決程序始能公告，目標12月完成，中間節點須留意時程」，而不是「須注意里程碑時程」這種沒有依據的提醒。

## 選材：什麼進紀錄

- 運作機制的決定：平台、看板、檔案存放位置、群組使用方式
- 會議安排的決定：頻率、時段、出席方式
- 個案的狀態變更、結論、下一步、負責人
- 具體參數：日期、時長、人數、金額、法規條號
- 結論的理由，但只限構成該結論基礎的事實。例如「建議不採用」保留「資料儲存於境外、台灣尚無落地機房、境外委外法規遵循困難」三項
- 未定案但已有下一步者，以「待議」「視指示再定」記錄狀態與下一步

## 選材：什麼不進紀錄

- 對人、單位、廠商或文件品質的評價與抱怨
- 組織內部的立場摩擦、名單增刪的過程、誰擋掉了誰
- 尚未產生決定或下一步的內部討論，且該案不在追蹤清單上者不列。若該案已在追蹤清單上，列入討論事項並註明「尚無結論」，不要因為沒有結論就整項省略
- 個別工具的即時排錯：連線、WiFi、API key、帳號權限
- 個人行程、請假安排、玩笑、寒暄
- **會議正式開始前與宣告散會後的談話，即使內容有實質性**。例會常在等人到齊的空檔先聊起來，那段與散會後同樣不入錄。實際發生過的錯誤是把會前閒聊中的一個議題列成新增議題
- **本次未及討論的案件整項不出現**。不寫「本次未討論」「維持前次狀態」。紀錄只記錄本次產生的內容，未動的案件由追蹤表承接
- **承辦內部作業一律不寫**。判準是：該事項若只在承辦之間流轉，對讀者不構成限制或前提，就不寫。主持與計時分工、報告人提交時程、幾點進場、派幾名同仁到場、場地網路開放到幾點，都屬此類。反面例子是「主管須於會前下載簡報」，它是當天能否操作的前提，要寫
- 過程性的抱怨描述。此類討論若構成本會議存在的理由，改寫為中性的目的敘述，不描述抱怨本身

最後一條是選材裡最需要判斷的一條，示範：

**逐字稿**：「我覺得現在資訊很多亂七八糟……可能 A 會議中也講一下這個議題，B 會議中也講一下這個議題，然後傳出來的資訊可能其實是不一樣的」「我從 A 管道拿到一個資訊，趕快開始做，做了一半發現這不是要做的」

**紀錄**：「鑑於專案推動涉及多元溝通與交辦管道，為提升資訊整合效率並強化跨單位協作，本會議將作為 PMO 進度對齊與資訊共享平台，定期彙整重要事項、同步執行進度，確保各項決議與訊息傳達一致。」

抱怨的**指向**被保留下來成為制度目的，抱怨的**內容**與情緒全部移除。

## 複核退改點

以下八項來自實際初稿與定稿的比對，是複核者反覆修正的地方。動筆時直接照做，不要等被改。

### 一、目的敘述不承認組織失能

最重要的一條。目的段只寫要達成的狀態，不寫現在有什麼毛病。負向詞一律轉為正向目標：

| 不寫 | 改寫為 |
| --- | --- |
| 交辦管道眾多，導致資訊碎片化且重複作業 | 專案推動涉及多元溝通與交辦管道 |
| 避免漏接交辦事項 | 定期彙整重要事項、同步執行進度 |
| 對齊各會議傳出的分歧訊息 | 確保各項決議與訊息傳達一致 |
| 資訊混亂、指令反覆 | 提升資訊整合效率、強化跨單位協作 |

句式：鑑於〔中性現況〕，為〔正向目標〕，本會議將作為〔定位〕，〔具體作為〕，〔預期效果〕。

紀錄會流通到主管層。在書面文件中承認「重複作業」「漏接」「訊息分歧」等於留下組織失能的紀錄，複核時一定被改。

### 二、不用監督性動詞描述同儕機制

這是同層級協作文件，不是管理控制文件。

- 追蹤機制 → 同步機制
- 用於追蹤各事項交辦進度 → 列示各項交辦事項及進度
- 管理、督辦、控管 → 彙整、分享、同步

### 三、不在紀錄中放寬出席義務

可選的只有出席**方式**，不是出席本身。即使會議上明確說了「可以來就來」「人可以 skip」，也不寫進紀錄。

- 不寫：採開放參加性質、無法出席者得不參加、非強制出席
- 寫：可依個人工作時間及地點選擇實體或線上與會

### 四、機制條文要附上對讀者的好處

只寫「要做什麼」會被退。補上做了之後對當事人的實益，理由要指向同儕的方便，不指向便於管理。

範例：「各位PMO交件前可先將檔案於群組中分享，方便互相查看與交流進度，**以利主管詢問時可先行回答**。」

### 五、補足受詞與限定語

初稿常留下需要讀者自行補完的省略。逐一補上：

- 課程規劃 → 8月課程規劃
- 功能比較 → Slack與Teams功能比較
- 推動委員會 → AI推動委員會
- 說明題型 → 說明及Demo工作坊題型
- 最後抽籤 → 最後抽籤9月工作坊題目
- 檔案存放於「AI策略藍圖推動」 → 相關檔案已存放於「AI策略藍圖推動」共用資料夾中

### 六、刪除可推得的內容與操作細節

- 前句已含蓄涵蓋者刪除。例如已寫「改事前分組」，就不必再寫「以組為單位作答」
- 軟體介面的操作路徑刪除。例如「可在群組『已共用』中直接開啟」
- 會議通知等行政細節刪除。例如「地點以會通為主」

### 七、對同儕用請與可，不用命令句與口語動詞

- 直接標「完成」 → 請標示「已完成」
- 先把檔案丟入此群組 → 可先將檔案於群組中分享
- 各單位 → 各位PMO（收件對象是人，不是單位）
- 狀態標籤依系統實際字樣，不自行簡寫

### 八、語音轉檔錯字要複查兩次

初稿也會漏。實際案例中「治安專場」在初稿仍未改為「資安專場」，是複核時才抓到。交付前針對機構名、產品名、同音專有名詞再核一遍，不要因為初稿讀起來順就跳過。

同時注意工具能力的事實錯誤：初稿寫「可自行新增欄位」，實際上 Loop 欄位型別固定，能自行新增的是交辦事項。凡涉及工具能做什麼，依逐字稿裡的實際說明寫，不憑常識推測。

## 語體

行政文書體。動詞優先，狀態詞明確，不用評價語。

慣用詞：已／尚未／將／後續／原則上／屬／視……再定／以利／鑑於／僅／另

改寫示範：

| 逐字稿 | 紀錄 |
| --- | --- |
| 合規面這邊就會建議不要 | 合規初步結論為建議不採用 |
| 他現在在台灣是沒有任何機房 | 台灣尚無落地機房 |
| 題目不改嘛，因為他只是換了那個抽籤的方法 | 題目已定，僅微調抽籤方式 |
| 大家如果覺得要放上去都可以自己放 | 請各位自行新增交辦事項 |
| 昨天取消的，一開始把後來在分組的時候…… | 取消當天抽籤，改事前分組 |
| 這個東西應該要在哪裡報，或是融合在他們自己的報告裡面報 | 規劃先在 AI 推動委員會（治理月會）討論並回報朱總，視指示再定 |

其他語體規則：

- 主體為 PMO 集體時用無主詞句：「已建立 Loop 看板」「已完成並交付」
- 不寫承接句與過渡句。項與項之間不需要連接
- 避免評價性用語：很好用、有問題、首例、教訓。改用中性詞：議題、影響、要求、前提、差異、限制、實務、依據
- 不使用破折號「——」。改用句號、逗號或冒號重組句子
- 各案進度每項以一至三句為度。寫不下就是選材沒收乾淨

## 人名與稱謂

- **與會人員**：一律使用名單上的全名
- **非與會人員**：保留逐字稿中的慣用稱謂，不擅自補全名。例如「張老師」「朱總」
- 語音轉檔的人名幾乎都是錯的。逐一對照與會人員名單校正。對不上名單、又無法從上下文確定的，標「待確認」並在交付時列出

## 術語校正

逐字稿常以「每字之間插入空白」的形式提供，處理前先移除中文字元之間的空白，再讀內容。

語音轉檔對英文產品名、機構名與同音詞的錯誤率極高，且同一場會議中同一個詞會有多種錯法。動筆前先通讀全文，建立本場的錯字對應，再開始寫。

常見對應見 `references/術語與人名校正表.md`。該表隨每場會議累積，遇到新的錯法一併補入。特別注意「治安」在此語境中幾乎都是「資安」的誤轉。

## 完整範例

`references/範例對照.md` 收錄一組完整的逐字稿與定稿對照。撰寫前讀過該檔，對照定稿的密度與語體，比讀規則有效。

## 交付前自我檢查

逐項確認，不要交半成品讓使用者代為檢查：

1. 壹貳是否為會議時間與與會人員，實質內容是否全在參底下
2. 是否殘留郵件語（各位主管好、檢送、敬請參閱）
3. 目的段是否殘留負向詞（碎片化、重複作業、漏接、分歧、混亂）
4. 是否用了追蹤、管理、控管等監督性動詞
5. 是否寫了出席可自由選擇
6. 報告事項節內是否混入了變更、分歧或未決事項。若有，移至討論事項
7. 討論事項節內是否有應標未決卻寫成已定案的項目
8. 每一項是否只含一類資訊
9. 是否出現逐字稿裡沒有的數字或事實
10. 機構名、產品名、同音專有名詞是否再核過一遍
11. 涉及工具能力的敘述是否依逐字稿實際說明，而非常識推測
12. 人名是否全部對照過與會人員名單
13. 受詞與限定語是否補足，無需讀者自行補完的省略
14. 是否殘留評價語或情緒性描述
15. 是否有承接句
16. 是否有破折號
17. 負責人是否由使用者提供而非自行推論
18. 每句朗讀是否通順

## 交付方式

預設直接以純文字輸出於對話中，便於貼入 Word 或郵件。使用者明確要求檔案時才產生 .docx。

標點一律全形：逗號「，」、分號「；」、冒號「：」、句號「。」。括號在定稿中全半形混用，無穩定規則，建議統一半形。

紀錄以郵件寄送，前後各有固定套語：

```
各位主管好：

檢送2026/8/6(四)「金控AI推動委員會PMO待辦事項討論例會」會議紀錄，敬請參閱。

〔紀錄本體〕

若有任何問題，再請聯繫我，謝謝！

Best,
```

交付時另附兩份清單，不要混在紀錄正文裡：

- **推論的負責人歸屬**：逐字稿無說話者標記時，列出各案負責人的推論依據
- **待確認項目**：無法解析的人名、術語、機構名，以及紀錄中標為「待議」的事項
